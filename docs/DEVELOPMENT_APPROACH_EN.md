# Build the game you want, then discover how far it can travel

After releasing these editions, NEON REVENANT's human creator described an approach for future projects based on this collaboration: first make an appealing, playable game on the most capable target machine; then move down through the hardware generations, concentrating on ways to preserve what makes that game worth playing. Remove detail, replace techniques, and test new ideas. When further compromises would destroy the core experience, stop extending hardware support and publish the editions that succeeded.

This article explains that approach through the project's four MSX configurations. It complements the [Japanese development notes](ASTRA_MSX_GAMEDEV_JA.md), which link the individual experiments to their implementation and verification records.

The first target was MSX turbo R with a V9990 cartridge. “Most capable” meant freedom within that specified machine, its native execution conditions, and a 512 KiB ASCII8 ROM. The reference had to boot and run as an MSX program. PC tools generated artwork during development; the running game uses the MSX CPU and video hardware. The “if MSX3 had existed” visual direction described an ambition for this target, without making a PC-rendered video the product to reproduce.

A working reference makes the next decision concrete. For this game, the important qualities included rushing through a night city, readable aircraft and enemies, responsive shooting, and a recognizable musical identity. The creator could point to an actual scene and ask whether a proposed port still delivered that feeling. An attractive version also gives the work momentum: there is already something enjoyable to return to while a difficult experiment is unfinished.

Preserving that version is part of the method. Each port has its own source directory, ROM, guide, and verification records. Experiments on older hardware do not require weakening the successful edition. Keeping previous builds also makes comparisons useful: the same action or scene can be checked against a known working result.

The four configurations illustrate different kinds of adaptation:

1. **[Turbo R with V9990](../outputs/README-ja.md).** This established the visual reference: buildings with visible faces, windows, road reflections, and forward-moving perspective backgrounds. Offline tools generated the images, compressed them for the ROM, and prepared them for native display and composition. The creator's feedback first improved the sense of movement, then the artwork.
2. **[Turbo R using its internal V9958](../turbor/README.md).** Removing the graphics cartridge required different rendering. Backgrounds became SCREEN 4 tables, with color restrictions, and aircraft became hardware sprite compositions. The edition retained the three stages and bosses while accepting changes such as fewer background phases and the removal of lateral background movement.
3. **[MSX2 using V9938 and a standard Z80](../msx2/README.md).** Here the background and aircraft pixels could be retained. Work focused on reducing repeated sprite transfers through caching and separating gameplay and music updates from rendering. Music was arranged for the standard PSG. Keeping a melody's identity became an explicit design constraint when changing the sound implementation.
4. **[First-generation MSX](../msx1/README.md).** Its 16 KiB VRAM required a larger change. The initial edition used resident tile patterns. PCG Drive v1.1 returned to the original moving scenery, using reduced geometry, fixed-color dithering, shared tile shapes, and streamed pattern updates. It prepares the next picture across two game frames while protecting currently visible patterns. The previous sprite shapes, PSG music, and game progression remain intact.

These steps offer three useful questions for a port: what can be removed without losing the experience, what can be replaced by a cheaper representation, and what can be preserved through a better implementation? The answer depends on the machine and the scene. Extra ROM space, for example, can hold prepared transfers, but it does not increase VRAM capacity or make transfers instantaneous.

Stopping needs the same attention as optimization. Define the qualities to preserve before each attempt, then assess the resulting game under representative play. If controls cease to feel responsive, threats become difficult to read, or the central sense of movement disappears, try a specific alternative and compare again. If workable alternatives still cannot preserve those qualities, end that port and release the successful versions. This is a decision rule for future work, not a claim that every older machine can reach a fixed standard.

ASTRA's role in this collaboration was to implement, measure, investigate failures, and revise bounded parts of the project. The human creator supplied direction and judged whether the result was still appealing. Recorded measurements inform that judgment; they do not replace it or establish a universal quality guarantee.

To make the process reusable, retain the original assets, conversion scripts, build instructions, machine configuration, ROM hashes, and test results. Record discarded approaches when they explain a useful tradeoff. Measure active gameplay separately from paused rendering stress tests, use emulated MSX time, and distinguish native captures from artwork previews. Read VRAM back to verify what was actually displayed. The published guides document these checks and their limits. Physical MSX hardware and cartridges remain untested; the releases are experimental and provided without warranty.
